# Solar Guardian 2.2.7 : capture et première lecture Python locale

> Les adresses LAN et noms Wi-Fi de ce document sont anonymisés et illustratifs.

## Résultat

Le 17 octobre 2026 à **19:27:17 Europe/Paris**, le PC a obtenu directement de
la clé, sur **192.168.1.100:8899**, des réponses Modbus RTU valides après une
initialisation native observée dans la capture Android. Aucun changement des
réglages Wi-Fi, série, TCP Client ou de l'onduleur n'était nécessaire.

| Fréquence réseau | 3504 | 5000 | 50,00 Hz |

| Courant sortie AC | 3522 | 116 | 1,16 A |
| Fréquence sortie AC | 3529 | 5000 | 50,00 Hz |

Division par 100 selon le document UP-HI référencé dans [protocol.md](protocol.md).
Les mesures sont cohérentes avec l'application et l'alimentation utility seule,
sans constituer une comparaison simultanée à un instrument de référence.
Les registres batterie lus étaient nuls, conformément à l'absence de batterie.
Pas de puissance active déduite du produit tension × courant.

## Ce que montre la capture fournie

- 1181 paquets ; deux sessions TCP vers **10.10.100.254:8899**.
- Initialisation native en début de session ; réponse de version **V1.0.17**.
  Ce champ de protocole n'est pas la version du firmware web de la clé.
- Ensuite, trames Modbus **RTU avec CRC**, sans en-tête MBAP ; unité **10**.
- Fonctions observées **01, 02, 04**, toutes des lectures. Aucune fonction
  d'écriture Modbus observée dans les requêtes extraites de ces sessions.
- 340 couples de lectures/réponses avec CRC valides, après regroupement de cinq
  requêtes adjacentes répétées. Une requête finale reste sans réponse appariée.
- 20 échantillons des principaux registres ; la tension réseau varie dans la
  capture de **232,57 à 245,38 V**. Cette variation ne représente pas une
  conclusion sur la qualité du réseau électrique.

Les flux TCP sont réassemblés par numéro de séquence ; trous, CRC incorrects et
longueurs incohérentes sont refusés. L'appariement repose sur l'ordre des requêtes
et réponses et les longueurs attendues ; ce parseur est ciblé sur cette capture,
pas un analyseur universel Modbus RTU/TCP. Les répétitions ont ici la même requête
adjacente, compatible avec des retries ; leur cause réseau exacte n'est pas établie.

## Pourquoi les premiers essais ne suffisaient pas

Le port 9999 avait été activé temporairement pour tester un transport transparent.
Le chemin utilisé par l'application est le **port natif 8899**, disponible même
quand le réglage réseau visible est TCP Client. Une lecture FC04 brute sur 8899
sans initialisation a aussi expiré ; la même connexion avec l'initialisation
capturée, puis les lectures, a réussi. On n'attribue donc plus les premiers
timeouts à un problème de câble ou d'identifiant.

## Outils reproductibles

```sh
python -m pip install -r requirements-capture.txt
python tools/analyze_solar_guardian.py chemin/capture.pcap
python tools/analyze_solar_guardian.py chemin/capture.pcap --live-host 192.168.1.100
```

Sans `--live-host`, aucun accès réseau vers la clé. Avec cette option, le programme
reproduit en mémoire l'initialisation native de cette capture, puis envoie
uniquement cinq lectures **FC04**, séquentielles et bornées. Ne pas utiliser la
capture d'un autre appareil : la négociation est liée à cette passerelle. Fermer
Solar Guardian avant un essai pour éviter une concurrence entre clients.

L'initialisation est traitée comme une trame opaque : son contenu n'est pas exporté
dans le rapport, ni incorporé dans le code. La signification de ses octets non
identifiants et la procédure générique de création de session restent à documenter.
Aucun déchiffrement TLS ni extraction de mot de passe n'a été réalisé.
Le PCAP original reste privé et exclu du dépôt.

Résultat brut et historique : `reports/solar-guardian-analysis.json` (non versionné).
Le service continu, la reconnexion et MQTT Discovery restent à développer après
cette preuve de concept ; aucune entité Home Assistant n'est encore publiée.
